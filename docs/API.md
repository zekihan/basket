# Basket: API Contract

Status — v1

Wire types, the operation protocol and the MCP tool schemas. Go
(`internal/basket/types.go`) and TypeScript (`web/src/types.ts`) must match this
file exactly. Rules live in [DESIGN.md](DESIGN.md); this file only fixes shapes.

## Conventions

- JSON field names are `snake_case`.
- Ids are 26-character Crockford base32 ULIDs (upper case). Clients may
  generate item and purchase ids; the server rejects malformed ids.
- Calendar dates are `YYYY-MM-DD` strings in the owner's time zone. Timestamps
  are RFC 3339 UTC with seconds (`2026-11-24T10:00:00Z`).
- Amounts on input are strings in the family-tab format (`"189,90"`,
  `"1.299,90"`, `"1299.90"`, `"1299"`). Amounts on output are a formatted
  string (`"1.299,90"`) plus the integer kuruş value in a `…_minor` field.
- Optional fields that are absent are `null` on output, never omitted.
- Errors use `{"error": {"code": "...", "message": "..."}}` with codes
  `invalid` (400), `unauthenticated` (401), `forbidden` (403), `not_found`
  (404), `conflict` (409), `internal` (500).

## Types

```ts
type ListName = "shopping" | "wishlist";
type Status = "open" | "bought" | "archived"; // derived status, see DESIGN 5

interface Item {
  id: string;
  list: ListName;
  title: string;
  quantity: number;               // 1..999
  notes: string;                  // "" when empty
  target_price: string | null;    // "1.299,90"
  target_price_minor: number | null;
  recurring_days: number | null;  // 1..730, shopping only
  status: Status;                 // derived (auto-archive applied)
  created_at: string;
  updated_at: string;
  version: number;
  last_purchase_date: string | null; // latest purchase date
  due_date: string | null;        // recurring with a purchase: last + recurring_days
  due: boolean;                   // status bought, recurring, due_date <= today
}

interface Purchase {
  id: string;
  item_id: string;
  date: string;
  price: string | null;
  price_minor: number | null;
  quantity: number;
  store: string | null;
  created_at: string;
}

interface Snapshot {
  today: string;          // in time_zone
  time_zone: string;      // IANA name
  items: Item[];          // every item, newest created first
  purchases: Purchase[];  // every purchase, newest date first, then newest created
  can_undo: boolean;      // the PWA actor has a change log row to revert
}

interface Me { subject: string; name: string | null; email: string | null; }
```

## Operations (`POST /api/ops`)

Request: `{"ops": Op[]}` with at most 200 ops. Ops are applied in order, each in
its own transaction. The server records every `op_id` it has applied together
with its result; a resent `op_id` returns the stored result with
`duplicate: true` and changes nothing. A failed op is recorded too, so a resend
never applies it later. Every op from `/api/ops` is logged with actor `pwa`.

```ts
type AmountInput = string | null; // null clears

interface ItemFields {
  list?: ListName;
  title?: string;
  quantity?: number;
  notes?: string;
  target_price?: AmountInput;
  recurring_days?: number | null;
}

type Op =
  | { op_id: string; type: "add_item"; id: string; fields: ItemFields & { title: string } }
  | { op_id: string; type: "update_item"; id: string; fields: ItemFields }
  | { op_id: string; type: "remove_item"; id: string }
  | { op_id: string; type: "mark_bought"; id: string; purchase_id: string;
      date?: string; price?: AmountInput; store?: string | null; quantity?: number }
  | { op_id: string; type: "add_purchase_details"; purchase_id: string;
      price?: AmountInput; store?: string | null }
  | { op_id: string; type: "reopen_item"; id: string }
  | { op_id: string; type: "archive_item"; id: string }
  | { op_id: string; type: "delete_purchase"; purchase_id: string }
  | { op_id: string; type: "undo" }
  | { op_id: string; type: "set_time_zone"; time_zone: string };

interface OpResult {
  op_id: string;
  ok: boolean;
  duplicate: boolean;
  error: { code: "invalid" | "not_found" | "conflict"; message: string } | null;
}

interface OpsResponse { results: OpResult[]; snapshot: Snapshot; }
```

Semantics:

- `op_id` is a ULID generated by the client.
- `add_item` from the PWA never blocks on similar items (the PWA shows the
  hint from `GET /api/similar`). Adding an id that already exists is
  `invalid`.
- `update_item` carries only the changed fields; each present field is written
  as-is (per-field last write wins by arrival). A field that is not present is
  untouched. Moving an item to `wishlist` clears `recurring_days`; setting
  `recurring_days` on a wishlist item (after applying `list` from the same op)
  is `invalid`.
- Any op on an item or purchase that no longer exists is `not_found`. This is
  how a delete wins over every edit of the same item.
- `mark_bought` logs a purchase with `purchase_id`; `date` defaults to today,
  `quantity` to the item's quantity. On a bought item it logs another purchase.
- `add_purchase_details` sets only the fields present.
- `archive_item` sets status `archived` from any status. `reopen_item` sets
  `open` from `bought` or `archived`.
- `undo` reverts the actor's most recent change log row (see Undo below).
  With none, it is `not_found`; a version mismatch is `conflict` and the
  message names the item title.
- `set_time_zone` validates an IANA name and is not written to the change log.

## Undo

Each mutation writes one change log row: actor, operation, timestamp, and the
before and after JSON of every item and purchase it touched (`null` for
absent). Undo takes the newest row of the same actor, checks that every touched
item's current version equals its after-state version (and that every touched
purchase currently equals its after state, or is absent when the after state is
`null`), then restores every before state. The restore increments the version
of restored items above any version they have had and writes its own row with
operation `undo`, so undoing again re-applies the original change. Rows older
than 30 days are pruned.

## Other routes

| Route | Response |
| --- | --- |
| `GET /api/snapshot` | `Snapshot` |
| `GET /api/similar?title=…` | `{"items": Item[]}` similar open items |
| `GET /api/export` | `{"exported_at", "time_zone", "items", "purchases"}` as an attachment `basket-YYYY-MM-DD.json` |
| `GET /auth/me` | `Me` or 401 |
| `GET /auth/login`, `GET /auth/callback`, `POST /auth/logout` | Sign-in redirects; logout returns 204 |
| `GET /healthz` | `200 ok` when the database answers |

## MCP tools

All tools act with actor `mcp`. Inputs are JSON objects; outputs are structured
JSON (the same `Item` and `Purchase` shapes) plus a short text summary. Errors
are tool errors with the message from the service.

| Tool | Input | Output |
| --- | --- | --- |
| `add_item` | `title, list?, quantity?, notes?, target_price?, recurring_days?, allow_similar?` | `{added: Item \| null, similar: Item[]}` |
| `add_items` | `items: (add_item input)[]` (1..50) | `{results: {title, added: Item \| null, similar: Item[], error: string \| null}[]}` |
| `list_items` | `list?, status? ("open" default, "bought", "archived", "all"), query?` | `{items: Item[]}` |
| `get_item` | `id` | `{item: Item, purchases: Purchase[]}` |
| `update_item` | `id, list?, title?, quantity?, notes?, target_price?, recurring_days?` | `{item: Item}` |
| `remove_item` | `id?` or `query?` (exactly one) | `{removed: Item \| null, candidates: Item[]}` |
| `mark_bought` | `id, price?, store?, date?, quantity?` | `{item: Item, purchase: Purchase}` |
| `reopen_item` | `id` | `{item: Item}` |
| `price_history` | `id?` or `query?` | `{item: Item, purchases: Purchase[], average_price: string \| null, average_price_minor: number \| null}` or `{candidates: Item[]}` when the query is ambiguous |
| `due_items` | `within_days?` (0..365, default 0) | `{items: Item[]}` with `due_date <= today + within_days` |
| `undo` | none | `{undone: string}` describing the reverted change |

- In `update_item`, an explicit JSON `null` clears `notes` (to `""`),
  `target_price` and `recurring_days`; an absent field is untouched.
- `query` matching uses the normalized title (DESIGN 5, Similar items): an item
  matches when every query token is a prefix of some title token. Queries
  match items of any status. Zero matches is an error; more than one returns
  `candidates` and changes nothing.
- `list_items` with `list` absent returns both lists, shopping first.
- Averages skip purchases without a price and are rounded half up to a kuruş.
